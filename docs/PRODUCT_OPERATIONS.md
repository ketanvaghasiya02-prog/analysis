# Product Operations Manual — Gap Research Terminal

> **Final document of the GRT v1.0 Master Specification.** All previous documents are
> frozen. This manual defines how GRT is released, deployed, maintained, versioned,
> documented and evolved. It does **not** modify any functionality.

## 1. Product identity

| Field | Value |
|---|---|
| Official product name | **Gap Research Terminal** |
| Short name | **GRT** |
| Subtitle | Professional CSV-Based Pair Spread Research Platform |
| Nature | Browser-based historical statistical research tool. **Not** a trading application — no broker connection, no orders, no signals, no predictions. |

## 2. Versioning policy

GRT follows **Semantic Versioning** (`MAJOR.MINOR.PATCH`):

- **MAJOR** — breaking architecture changes (e.g. `2.0.0`).
- **MINOR** — new research modules, backward compatible (e.g. `1.1.0`).
- **PATCH** — bug fixes only (e.g. `1.1.1`).

Example progression: `1.0.0 → 1.1.0 → 1.1.1 → 2.0.0`.

The current release is **`1.0.0`** (`package.json#version`). Engine/document version
constants live in `eaExport.ts` and `reportEngine.ts` and must move with releases.

## 3. Release types

`Development → Internal Testing → Beta → Release Candidate → Production → Archived`.

A build advances only when it satisfies the release checklist (§4) and the mandatory QA
gate (§5).

## 4. Release checklist

Before **every** release, verify each subsystem behaves and is CSV-reproducible:

- [ ] Research Engine
- [ ] Probability Engine
- [ ] Reliability Engine
- [ ] Validation Engine (Walk Forward)
- [ ] Reports
- [ ] AI Assistant
- [ ] EA Export
- [ ] Universal Search
- [ ] Market Context
- [ ] Performance
- [ ] Documentation

## 5. Mandatory QA

No release is permitted unless the [Quality Assurance framework](QUALITY_ASSURANCE.md)
returns **Release Approved**:

- All CSV validations pass.
- All deterministic calculations verified (same input → identical output).
- Regression testing completed.
- No **Critical** bugs.
- Performance targets achieved (§14).

Run it in-app at **Settings → Quality Assurance** or via `runQa()`; export the Quality
Certificate and attach it to the release.

## 10. Backup policy

Protect and never lose: the **Research Repository**, **research profiles**, **exports**,
**configuration** and **application settings**. The Repository exposes a full backup
(`repositoryBackup`); EA Export profiles and the QA certificate are durable artifacts.
Settings persist in `localStorage` and are included in routine backups.

## 11. Recovery plan

- **Repository recovery** — re-import a Repository backup JSON, or re-run the Historical
  Strategy Finder to rebuild from CSV (research is deterministic, so it reproduces).
- **Configuration recovery** — settings live in `localStorage`; restore from a settings
  export or reset to documented defaults.
- **Export recovery** — exports are reproducible: the same research + EA Export produces
  an identical content checksum, so any lost export can be regenerated byte-for-byte.
- **Application recovery** — a static client build; redeploy the artifact. No server
  state to restore.

## 12. Security policy

- **Validate uploaded CSV** — strict column/type checks in the parser; malformed rows are
  rejected and surfaced, never silently trusted.
- **Prevent invalid files** — non-CSV / unparseable input is refused.
- **Never execute uploaded content** — CSV is parsed as data only; nothing is `eval`-ed.
  The EA Export deliberately emits configuration data and **never** executable code.
- **Protect exported research** — exports carry a deterministic checksum for integrity.
- **Sanitize all user inputs** — query parsers, HTML/print renderers and exporters escape
  user-supplied values; processing is entirely client-side (data never leaves the browser).

## 13. Logging & error reporting

Maintain **Application, Research, Export, Validation and Error** logs. The EA Export log
and QA results are persisted; runtime errors should be captured with: **Module, Timestamp,
Version, User Action, Error Type, Stack Trace, Recovery Status**.

## 14. Performance targets

Measured by the QA performance suite and release testing:

| Operation | Target |
|---|---|
| CSV import (per 100K rows) | responsive, worker-parsed |
| Research execution | sub-second per combo on golden data |
| Probability generation | < ~400 ms on ~1K samples |
| Repository search | instant (indexed, memoized) |
| Report export | immediate |
| Memory usage | bounded; no leaks across navigation |
| Application startup | fast first paint |

## 15. Maintenance policy

`Bug fix → Regression test → CSV validation → Release`. Every bug fix adds a **permanent**
regression check (QA framework) so the bug can never reappear.

## 16. Deprecation policy

Never silently remove a feature. **Mark deprecated**, **document the replacement**, and
**remove only in the next major release**.

## 17. Future development policy

No new feature enters **v1.x** unless: architecture review completed, research methodology
approved, CSV validation defined, and testing defined. Anything outside v1 scope belongs to
the [V2 Backlog](V2_BACKLOG.md) and must not modify the v1 roadmap.
